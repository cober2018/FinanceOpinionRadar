## Context

`/open/v1/video-summaries` 已提供游标增量拉取；视频总结 Webhook 已复用通用渠道，并使用同一事件载荷。开放接口页面已有 Key、渠道、订阅开关与投递列表，但只在单个说明框中提及接口和事件，二者的定义与当前配置状态混在一起。

## Goals / Non-Goals

**Goals:**

- 让操作者在开放接口页面直接找到拉取 API、推送事件和各自的使用条件。
- 把固定的接口/事件契约与实时的渠道订阅状态清楚对应起来。
- 保持页面所述字段、鉴权、时间和撤回语义与现有后端一致。

**Non-Goals:**

- 不提供运行时编辑、发布或版本化接口定义的后台。
- 不新建 API、数据库表、推送协议或测试代码。
- 不把渠道投递成功解释为下游业务消费成功。

## Decisions

1. 在现有 `OpenApiPage` 内把说明框改成独立的“数据 API”和“推送事件”区块，使用页面内静态契约内容。接口是已发布的代码契约，若再建立数据库定义表会引入双份真相；方案通过前端构建校验和人工契约核对降低文案漂移风险。
2. API 区块列出增量列表和兼容的单视频查询，说明 `X-API-Key`、`cursor`/`next_cursor`、分页及 `ready`/`withdrawn`。事件区块列出视频总结事件载荷、签名头、`event_id` 去重、`video_time`/`time_basis`、空值和撤回语义。
3. 订阅状态从现有 `/open-admin/push-channels` 响应计算，明确“已定义事件”和“已配置接收渠道”是不同状态。沿用现有创建、启停和投递列表，不增加新的管理端点。

## Risks / Trade-offs

- 静态页面契约可能随后端变化而过时 → 实施时逐字段核对 `serialize_event`、拉取路由与推送签名代码，并在后续变更中同步维护。
- 现有列表只返回最近投递记录 → 页面仅称“最近投递”，不据此断言完整消费状态。

## Migration Plan

仅更新前端静态页面及 README；构建后切换页面即可，回退可恢复前一版前端产物。无数据库迁移或下游协议迁移。

## Open Questions

如果用户希望操作者能编辑并发布接口或事件定义，需要另立契约治理需求；本提案按展示与现有订阅管理处理。
