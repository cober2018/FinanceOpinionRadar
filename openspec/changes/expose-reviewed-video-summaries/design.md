## Context

`SourceItem.viewpoint_summary` 和 `summary_generated_at` 已保存整条视频的总结；`GET /open/v1/items/{item_id}/summary` 已按 `X-API-Key` 返回主播、视频时间与总结。总结由已确认观点生成，`candidate/needs_review` 阻断生成，`rejected` 作为误报不参与。现有 `PushChannel` / `PushDelivery` 是逐观点投递，不能直接代表一条视频总结。工作树有其他未提交改动，实施时必须保留。

## Goals / Non-Goals

**Goals:** 同时提供分页增量拉取和自动 Webhook 推送；两者使用同一视频总结版本与字段；只交付复核完成且仍有效的总结；可辨认更新、重复、失效和未知投递结果。

**Non-Goals:** 不输出每条观点在视频内的发言时间；不重新审核总结文本；不自动向媒体平台发布内容；不改变既有逐观点推送的语义。

## Decisions

### 1. 建立单一的对外总结版本，而非分别临时组装拉取和推送

每次成功生成或重新生成总结，在同一事务中固化一个视频级交付版本：`item_id`、单调版本号、主播名称、视频时间与 `time_basis`、总结、已确认观点集合指纹、生成/更新时间和稳定事件 ID。拉取列表、单视频详情和推送都从这个版本的同一序列化器读取。旧版保留作为投递/对账依据，当前版资格单独判断。复用现有 `SourceItem` 总结字段作为控制台展示；对外版本是独立的稳定交付事实。备选“直接按 SourceItem.updated_at 扫描”无法可靠区分观点变化、总结版本和重试，故不采用。

### 2. 资格门禁与失效独立于模型生成

只有至少一条 `confirmed`、没有 `candidate/needs_review`、存在非空总结且总结记录的已确认观点指纹与当前集合一致，才是可交付的 `ready` 版本。复核结果变动、撤回、重新进入待审或来源失效时，当前可用版本转为 `withdrawn`，拉取变更流和推送均发送同一失效事件，避免下游继续把旧总结当作最新结论；重新生成后用新版本恢复。没有完成总结时不返回伪造的空结论。人工驳回的误报不进入指纹和总结。备选“只要 summary 非空就对外”会泄漏过期结论，故不采用。

### 3. 统一视频时间，不造逐条观点时间

外部字段 `video_time` 采用来源条目可核对的视频级时间：直播优先开播时间，普通视频使用已有 `published_at` 作为来源提供的公开视频时间；同时返回 `time_basis`（`live_started_at` / `published_at` / `unknown`）。无可靠时间时为 `null`，不使用转录片段偏移或接口调用时间代替。现有详情接口的 `published_at` 继续保留兼容，新增统一字段不破坏 `/open/v1` 已有字段。

### 4. 拉取用稳定变更游标，推送用独立投递状态

新增 `/open/v1/video-summaries`，按不可变事件序号/ID 升序分页，游标指向最后已读取事件；返回 `ready` 与 `withdrawn` 事件，支持初次全量和之后增量，客户端可按 `item_id` + `version` 幂等更新。新事件出现时旧游标仍有效，结果不受视频发布时间排序影响。对单视频查询保留既有路径，并增加当前版本/资格字段。

开放接口控制台为已授权的通用 Webhook 渠道显式开启“视频总结”订阅；既有逐观点渠道默认不订阅。按 `channel_id + event_id` 记录投递与尝试次数，携带稳定事件 ID、签名和版本。非 2xx/超时不能假定对方未收到：超时标为 `unknown`，先按事件 ID 对账或由操作员明确重试；明确失败按上限退避重试并可见。推送与拉取都提供同一事件，接收方可以拉取补漏。备选复用 `PushDelivery.viewpoint_id` 会混淆投递粒度，故不用。

## Risks / Trade-offs

- [已有视频总结没有观点指纹] → 迁移后标为待回填；只在可验证当前复核集合与总结生成时间时建立可交付版本，否则重新生成，不批量假定旧总结有效。
- [外部系统已保存旧结论] → 显式 `withdrawn` 变更事件；拉取和推送都支持接收方撤回旧版。
- [Webhook 造成内网访问或秘密外泄] → 沿现有安全配置增加目标地址校验、HTTPS/私网限制、签名、超时和审计；管理端不回显密钥。
- [推送结果未知] → 保留未知状态和稳定事件 ID，禁止无标识的盲目重复投递；接收方按事件 ID 幂等。
- [来源时间语义不统一] → `time_basis` 明示，缺失返回 `null`；不把普通视频发布时间声称为实际录制开始时刻。
- [手动删除与交付快照留存冲突] → 明确手动删除时擦除该视频历史 ready 载荷及其投递明细，只保留不含内容的最小撤回标记，以通知已消费的下游移除旧结论；自然到期清理仍按原保留策略处理。

## Migration Plan

先新增版本/事件与投递记录并迁移，不启用任何新订阅；随后部署统一序列化器、增量拉取与单视频兼容读取，再开放订阅管理及后台投递。旧逐观点推送原样运行。用少量已核对视频验收准备、更新、失效、重试与补拉后才启用对外订阅。回退时停用新订阅和新路由，保留已写版本/投递记录供审计，不删除已有 SourceItem 总结。

## Open Questions

实际对接方的 Webhook 地址、认证方式和接收回执协议在实施/联调时确定；第一版契约按通用 HTTPS Webhook、HMAC 签名与事件 ID 幂等制定，不因目标尚未提供而扩大范围。
